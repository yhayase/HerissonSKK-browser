# 開発ロードマップ

本書は、ブラウザ向け汎用 SKK 入力拡張機能の開発状況と、合意したマイルストーンを管理します。アーキテクチャと技術的方針は[アーキテクチャ](./architecture.md)を参照してください。

## 開発方針

最低限使える状態で日常試用を始め、実環境で初めて分かる課題を基に改善します。ストア掲載前の導入経路を使い、試用と並行して申請資料を準備します。ブラウザごとに提出条件を満たし次第、審査を依頼し、通過したものから順次公開します。全環境の完成や全機能の実装は待ちません。

初回公開後の具体的な改善項目と順序は、試用結果や利用者からの報告を基に相談して決めます。ファジング全体、候補 UI・設定の充実、共通ライブラリ化を、一律に試用開始や初回公開の前提にはしません。

## マイルストーン

| 順序 | マイルストーン | 到達条件 |
| :--- | :--- | :--- |
| **M1（直近）** | **日常試用の開始** | PC の Chrome・Firefox、物理キーボードを使う Android の Firefox で継続利用できる状態にします。 |
| **M2** | **初回審査への提出** | 基本入力・変換・登録ができ、文字や辞書が失われる既知の不具合がなく、対応範囲と制約を説明できる状態で、準備できたブラウザから提出します。 |

| **M4** | **日常利用の改善版** | 試用・公開後の報告から対象課題を決め、主要な支障を解消した更新版を配布します。具体的な対象と優先順位は今後相談します。 |

### M1: 日常試用の開始

実施手順と環境別の結果は[日常試用の確認記録](./daily-trial.md)で管理します。

対象は PC の Chrome・Firefox と、物理キーボードを使う Android の Firefox です。Android のソフトウェアキーボード対応は計画に含めません。次を実環境で確認し、不足する部分を試用開始までの作業として取り出します。

- **導入と継続利用**: インストールでき、ブラウザ再起動後も辞書・学習を保持して使えることを確認します。
- **基本入力**: 起動、かな入力、変換、候補選択、確定、キャンセル、辞書登録を確認します。
- **Android の物理キーボード操作**: `Shift` との同時押し、`Ctrl+j`、`Ctrl+g` が使え、候補表示と登録画面が操作を妨げないことを確認します。
- **更新**: 修正版へ更新しても個人辞書と設定を引き継げることを確認します。

ストア掲載前の日常試用には、次の導入経路を使います。これは導入方法の整理であり、本拡張の各実機での動作確認が完了したことを意味しません。

| 環境 | 試用の導入経路 |
| :--- | :--- |
| Chrome / PC | 開発者モードで展開済み拡張機能を読み込みます。 |
| Firefox / PC | Mozilla の署名を受けた非掲載版 XPI を導入します。 |
| Firefox / Android | 署名済みの非掲載版 XPI を「ファイルから拡張機能をインストール」で導入します。 |
| Chrome / Android | 通常の製品版は拡張機能に非対応のため、今回の試用対象に含めません。 |

導入経路の確認資料（2026-09-11）: [Chrome の配布方法](https://developer.chrome.com/docs/extensions/how-to/distribute)、[Firefox の署名と配布](https://www.extensionworkshop.com/documentation/publish/signing-and-distribution-overview/)、[Firefox の自己配布版の導入手順](https://extensionworkshop.com/documentation/publish/install-self-distributed/)、[Chrome のモバイル端末での制約](https://support.google.com/chrome_webstore/answer/1698338?hl=en)。Firefox の非掲載版も署名のための提出が必要で、審査ポリシーの対象です。

### M2〜M3: 審査提出と順次公開

申請資料の準備は日常試用と並行して進めます。試用終了後に準備を始めるのではなく、提出条件を満たしたブラウザから審査を依頼します。審査待ちの間も、ほかの環境の検証と改善を続けます。

- **提出条件**: 基本入力・変換・登録ができ、文字や辞書が失われる既知の不具合がなく、対応範囲と制約を説明できることとします。
- **申請準備**: 申請用パッケージ、ストア説明文、アイコン、スクリーンショット、利用方法、既知の制約、不具合の報告方法を整えます。
- **プライバシーポリシー**: 変換はローカル処理であること、外部辞書の取得・更新時には配信先へ通信することを説明します。
- **公開順序**: Chrome と Firefox の同時公開は条件にせず、審査を通過したものから公開します。対応すると記載する環境は実際に確認した範囲に合わせます。

基本操作が行き詰まる、候補が見えず選択できない、通常の操作を妨げて回避できないなどの問題は、公開前に解消する対象です。テーマ、設定項目の充実、操作可能な候補一覧の磨き込みなどは、実際の支障に応じて公開前後の扱いを判断します。

### M4: 日常利用の改善版

自分の試用と公開後の報告から、入力・変換・登録、候補の見やすさ、サイトとの競合などの課題を整理します。対象と優先順位を相談し、修正を含む更新版を配布します。すべての要望の実装は完了条件にしません。

入力破損や状態遷移の不具合には再現テストを追加します。ファジング、候補 UI、サイト制御や入力設定は、判明した課題に応じて取り込みます。特定の Web アプリの一覧や、これらの機能の実施順は現時点では固定しません。

### Phase 3: 辞書ストレージ & 検索エンジン (IndexedDB)・Firefox E2E（完了 ✅）

- **目的**: ネットワーク通信を行わず完全ローカル・オフラインで動作する高速な SKK 辞書システムを構築し、複数タブ間でのユーザ辞書同期とインライン再帰辞書登録を実現する。また、Gecko エンジン固有の挙動差異（キャレット座標、`insertText`、フルスクリーン等）による手戻りを防ぐため、Firefox でのヘッドレス E2E 自動結合テスト環境をこの段階で導入・完備する。
- **実装内容**:
  1. **SKK 辞書モデル・パーサーの移植 (標準形式)**:
     - `candidate.ts`, `entry.ts`, `okuri.ts`, `types.ts` 等のモデルとパースロジックを `src/core/skk/jisyo/` に環境非依存で移植。
     - 従来の標準 SKK 辞書形式（EUC-JP / UTF-8、`skk-dev/dict`）のパース処理（`JisyoParser.ts`）の実装（文字列パーサーとして純化）。
  2. **システム辞書ストレージ（IndexedDB）の実装**:
     - `public/dict/SKK-JISYO.S` などの辞書を IndexedDB の `system_jisyo` ストアにインデックス付きで格納。
     - 見出し語による高速完全一致および前方一致クエリ（`IDBKeyRange.bound`）の実装（クエリ応答時間 1〜3ms を達成）。
     - 辞書インポート完了状態（`system_metadata`）の管理と中断・破損時の自動復旧。
  3. **ユーザ辞書ストレージ & 拡張機能コンテキスト分離の実装**:
     - 登録単語および確定履歴（学習・候補並び替え）の IndexedDB (`user_jisyo`) 永続化（ACID トランザクション保証）。
     - Web ページのスクリプトからユーザ辞書を隔離・保護するため、IndexedDB を Background Service Worker に集約し、Content Script からは RPC プロキシ（`RemoteJisyoStore`, `RemoteUserStore`）経由で透過利用するアーキテクチャを確立。
     - 一意な `mutationId` による複数タブ間の同期メッセージ重複排除とエコーバック防止。
  4. **インライン辞書登録 & 再帰的辞書登録の実装**:
     - フォーカスを外さずに Shadow DOM 内のモーダルおよびミニバッファで単語を登録する `RegistrationMode` / `RegistrationModal`。
     - 辞書登録中に未知語に遭遇した際の再帰的辞書登録セッション（スタック管理、最大ネスト深度ガード付き）。
  5. **初期辞書ロード & Content Script 統合**:
     - 拡張機能バンドル辞書（公式 `SKK-JISYO.S`）の初回自動インポート機構（`DictionaryLoader.ts`）。
     - `entrypoints/content.ts` への `CompositeJisyoProvider` 統合。
     - 合成キーイベントを遮断する `isTrusted` ガードおよび非同期検索の世代管理。
  6. **Firefox (Gecko) ヘッドレス E2E 自動結合テストの導入と差異解消**:
     - Firefox (Gecko) 用ビルド（`wxt build -b firefox`）の自動実行と `geckodriver` によるヘッドレス E2E テスト環境（`test/firefox-verify.mjs`）の構築。
     - Chrome / Firefox 双方での全入力要素（`<input>`, `<textarea>`, `contenteditable`, Monaco Editor）およびインライン辞書登録・学習の自動テスト（全10件）がパスすることを確認済み。
- **検証結果**:
  - 全 377 件の単体テスト、Chrome E2E（5件）、Firefox E2E（5件）の全シナリオテストがエラー 0 でパス。Codex CLI レビュー指摘（P1 4件、P2 5件）および事後 PR レビュー指摘の改修・独立検証をすべて完了。

### Phase 3.1: JSON 辞書ローダー & IndexedDB データフォーマット検討（完了 ✅）

- **目的**: [skk-dict/jisyo](https://github.com/skk-dict/jisyo) で策定されている新世代の JSON 辞書形式（`SKK-JISYO.*.json`）の読み込みに対応するとともに、IndexedDB 上での最適なデータ保持構造（単一キーによる統一インデックス vs `okuri_ari` / `okuri_nasi` のストア分離等）を性能・容量・検索要件の観点から定量的に比較・検証し、今後の辞書拡張およびライブラリ化に向けた基盤を確立する。
- **タスク一覧**:
  1. **JSON 辞書パーサー / ローダー (`src/core/skk/jisyo/`)**:
     - `skk-dict/jisyo` のスキーマ仕様（`jisyo.schema.v0.0.0.json`）に準拠した JSON 形式辞書の読み込みおよびパース機能。
     - 環境非依存なデータモデルへの変換と、ストリーミング・分割読み込みによるメモリ消費抑制の考慮。
     - Vitest による JSON パーサーの網羅的単体テスト。
  2. **IndexedDB 上のデータフォーマット比較 & ベンチマーク**:
     - 次の構造パターンを同一データ・同一クエリで比較し、主要検索経路で一貫した改善がなく取得レコード数も増える分割方式 B ではなく、単一ストア方式 A を採用：
       - **パターン A (現行統一方式)**: 見出し語（送り仮名ブロックを含む）を単一キーとして 1 つのオブジェクトストアに格納。
       - **パターン B (送りあり/送りなし分割方式)**: JSON 辞書の論理構造に倣い、`okuri_ari` と `okuri_nasi` を別ストア（または複合インデックス）に分離。
     - **評価基準**:
       - 固定した v3 production store に対する完全一致・前方一致の相対レイテンシ
       - 前方一致検索（補完候補取得）走査時のカーソル走査コスト
       - 大容量辞書（`SKK-JISYO.L` 等）インポート時のパース・シリアライズオーバーヘッドおよび IndexedDB のストレージ使用量
       - ユーザ辞書（学習・登録）や外部辞書（標準テキスト形式・JSON 形式）との整合性・マイグレーション容易性
  3. **ストレージ層のリファクタリング & 移行パス**:
     - 辞書 ID・generation・見出しを複合キーにした v4 スキーマと、投入完了後に generation を公開する安全な更新処理を実装。
     - v1〜v3 のシステム辞書・ユーザー学習を保持する移行と、標準テキスト形式・JSON 形式辞書の透過的な共存を実装。
- **完了条件**:
  - `skk-dict/jisyo` の公式 `SKK-JISYO.S.json` 3,379見出しを正常にインポート・変換できることを Chrome / Firefox で確認済み。
  - [ストレージ比較結果](./dictionary-storage-benchmark.md)と[production 検証結果](./phase31-production-verification.md)を記録し、全404件の単体テスト、Chrome E2E 5シナリオ、Firefox E2E 5シナリオが継続してパスすることを確認済み。

- **改善候補**: 独立した候補一覧の表示、長い候補の可読性、狭い画面での配置、スクロール追従、ダーク・ライトテーマ対応を検討します。
- 旧計画の「1〜9 による選択」は既存操作からの仕様変更になるため、採用を前提にせず、必要性を相談します。

### Phase 6: 設定・ドメイン制御（一部実装済み）

- **実装済み**: システム辞書の構成管理、外部取得・ローカルインポート、候補診断、ポップアップの辞書状態表示と設定画面への導線があります。
- **残る項目**: サイト単位の有効・無効、起動キーバインド、確定キー・句読点などの入力設定、個人辞書のインポート・エクスポート・削除を検討します。
- 既存のシステム辞書管理と未実装の個人辞書管理を分けて扱います。設定を追加する際には、既存の辞書設定と同様に変換中の候補保持やタブ間の反映を考慮します。
- 旧 Phase 6 の公開準備は M2〜M3 で扱い、設定機能全体の完成は提出条件にしません。

## 将来構想: 提供形態の拡張とライブラリ化（旧 Phase 4）

拡張機能を入れられない環境で bookmarklet としてページへ注入する形や、Web アプリケーションへ直接組み込む形を将来の可能性として残します。どちらも構想段階で、実現性、着手時期、優先順位は未定です。

`skk-vscode` は現時点では更新終了の方向で考えており、双方のコード共有を目的としたライブラリ抽出は当面の計画に含めません。VS Code 拡張では介入できる範囲がエディタ領域に限られることが、ブラウザ版を進める背景です。

- 当面は `src/core/` の環境非依存性を保ちます。
- bookmarklet やアプリ組み込みを具体的に試す段階で、入力処理、辞書の保持方法、コアとの境界を検討します。
- 具体的な用途が固まるまで、独立パッケージ化、公開 API、リポジトリ構成、ESM / CJS 対応などは決めません。将来構想だけを理由に抽象化を増やしません。
- ライブラリ化を初回公開や日常利用の改善版の前提にはしません。
